# Prardhana: MVP audit and execution roadmap

25 October 2026. Audited the current working tree, including uncommitted 0.6.2 changes, Android Java/SQLite implementation, Node services, tests, local design briefs and eight exported mockups. Existing user changes were preserved. This is an audit and proposed roadmap, not an implementation.

**Decision: freeze feature expansion. The product cannot make a trustworthy spending claim while its amount parser can select a balance and its correction UI cannot repair the amount.** The 55-screen proposal makes this harder by adding accounts, backup, forecasts and identity inference before the underlying ledger is dependable.

Evidence labels below distinguish **reproduced** synthetic failures, **code-confirmed** behavior, **design-only** flaws and **risks requiring device validation**. Historical research claims were not independently revalidated against private SMS dumps. No raw SMS datasets, credentials or live pilot database were needed for this audit. Mockups are proposals, not evidence of current Android behavior.

## STEP 1: DECONSTRUCTING THE DATA-DUMP

### 1. Core Value Loop

**Single user action: confirm or correct the few captured payments that materially change their understanding of recent money out.**

The loop is: choose a source → import locally → see recorded outflow and its coverage → clarify a high-impact entry → see the corrected total. A repeat visit should reveal new activity and unresolved uncertainty without requiring another setup journey.

The MVP promise should be: “Understand the payments captured on this phone, and correct mistakes.” It cannot promise a complete financial ledger, live balances, verified bills or an amount safe to spend. Notifications and SMS are incomplete observations; the source can be missing, late, duplicated or ambiguous.

Use three destinations: **Home, Activity, Settings**. Transaction detail is a screen or sheet within Activity. A short source-selection/import flow precedes first use. Home contains the selected month, recorded outflow, capture/coverage status, up to five important review items, and recent activity. Budget is optional and subordinate until the underlying outflow is understood.

### 3. System Friction

- **First use:** current users must discover Settings, distinguish inbox permission from future SMS capture, optionally leave the app for notification access, then import. The proposed sign-in/language/privacy/bank-discovery/reveal/quick-setup chain adds more gates. Replace it with source choice → just-in-time disclosure/permission → import progress → useful result. Offer manual entry/paste when access is declined.
- **Recovery:** paste currently saves directly after extraction; it is a parser test dialog masquerading as transaction entry. Show an editable preview before commit.
- **Review:** one dialog presents provenance, name, 24 category choices, direction, remembered rules, group review, reporting and deletion, but no amount editor. Offer “Correct amount,” “Own transfer,” “Exclude,” and “Confirm”; put advanced classification and metadata behind disclosure.
- **Review volume:** a missing payee is not automatically an actionable error. Rank by financial impact and ambiguity; do not require naming every small payment. Allow skip without implying failure.
- **Navigation:** rebuilding the entire view tree after each action discards the current scroll context; ordinary Activity fields hold search, busy and navigation state. Restore location and draft changes across rotation and process recreation.
- **Capture status:** not configured, permission denied, importing, active, disconnected, interrupted and no matches are different states. A zero figure is inappropriate as the first explanation for all of them.

## STEP 2: TECHNICAL & LOGICAL FLAW IDENTIFICATION

### Release blockers and architectural bottlenecks

**F01 — P0, reproduced: incorrect monetary extraction.**

The parser takes the first currency match rather than binding the amount to the executed movement. Synthetic probe:

```text
Available balance INR 9000. Your A/c XX1234 debited INR 500 at Cafe ref TEST123456
Actual: 900000 paise / debit. Expected: 50000 paise, or abstention if unsupported.

Your A/c XX1234 debited INR 500 at Cafe ref TEST123456. Available balance INR 9000
Actual: 50000 paise / debit.

Your A/c XX1234 debited INR 10.999 at Cafe ref TEST123456
Actual: 1000 paise / debit. Expected: reject malformed monetary token.
```

These are synthetic counterexamples, not a measured error rate on real bank messages. Fix whole-token validation and amount-role extraction; multiple plausible amounts must cause abstention/review. Add regressions for reversed field order, limits, balances, fees, malformed decimals and multiple currencies. [TransactionParser](C:/Users/nande/Downloads/Prardhana/app/src/main/java/in/prardhana/app/TransactionParser.java:46).

**F02 — P0, code-confirmed: wrong amounts cannot be repaired.**

The editor changes name/category/direction; `Store.review` does not accept amount or effective date. A user can report `wrong_amount`, but that does not repair their own ledger. Add validated integer-paise overrides, explicit date provenance, save failure state and undo. Re-import/parser upgrades must preserve overrides without replacing original evidence. [Editor](C:/Users/nande/Downloads/Prardhana/app/src/main/java/in/prardhana/app/MainActivity.java:116), [review write](C:/Users/nande/Downloads/Prardhana/app/src/main/java/in/prardhana/app/Store.java:157).

**F03 — P1, code-confirmed: event resolution is not reversible with its evidence.**

Reconciliation writes `movementId` and “Paid / received.” Deleting that movement removes movement/evidence rows but leaves the event. Changing its direction or excluding it similarly does not re-evaluate the event. Events can retain a paid claim with invalid evidence. Invalidate/recompute automatic resolutions in the same mutation transaction; preserve separately identified user-confirmed statuses. Test event → matched debit → delete/exclude/change direction → status re-evaluation. [Reconciliation](C:/Users/nande/Downloads/Prardhana/app/src/main/java/in/prardhana/app/FinancialEvents.java:32), [deletion](C:/Users/nande/Downloads/Prardhana/app/src/main/java/in/prardhana/app/LedgerDb.java:72).

**F04 — P1, code-confirmed architecture; latency unmeasured: SQLite does not make the UI asynchronous.**

`MainActivity` queries SQLite and parses JSON on the UI thread. Balance and recurring screens load the entire ledger. “Show 100 more” rebuilds all prior rows in a `LinearLayout`, without recycling. Search uses `%term%` over serialized JSON, so indexed storage does not provide indexed text search. Move queries off the UI thread; use typed results, bounded pages and a recycled list. Query summaries directly. Measure before adding FTS. [Rendering and search](C:/Users/nande/Downloads/Prardhana/app/src/main/java/in/prardhana/app/MainActivity.java:95), [database search](C:/Users/nande/Downloads/Prardhana/app/src/main/java/in/prardhana/app/LedgerDb.java:43).

**F05 — P1, code-confirmed gap; concurrency scenario untested: capture is not durably accepted.**

Notifications enter an in-memory 256-item queue. Queue rejection records a Settings warning but does not persist the lost item; process death loses pending jobs. SMS uses a separate thread per broadcast and waits on the global `Store.class` lock shared with 500-message import batches. Its callback lacks the generation check used by other writers: a delayed pre-reset SMS can write after capture is re-enabled. Android's asynchronous receiver work remains subject to execution deadlines. Persist a minimal normalized observation/identity before acknowledging acceptance; route writes through one owner; use generation checks and bounded recovery. Do not persist the entire inbox to solve this. [Queue](C:/Users/nande/Downloads/Prardhana/app/src/main/java/in/prardhana/app/LedgerWork.java:7), [SMS receiver](C:/Users/nande/Downloads/Prardhana/app/src/main/java/in/prardhana/app/SmsReceiver.java:19), [Android receiver contract](https://developer.android.com/reference/android/content/BroadcastReceiver.html).

**F06 — P1, code-confirmed: ingestion has partial-commit windows.**

Live capture observes events and diagnostics before writing the movement; row updates, aliases and reconciliation are separate operations. A failure can leave only part committed. Import uses a transaction for the batch, but reconciliation runs after it. Keep observation, identities, movement and derived-state invalidation atomic; run widget/UI notifications only after commit. [Live capture](C:/Users/nande/Downloads/Prardhana/app/src/main/java/in/prardhana/app/Store.java:12), [import](C:/Users/nande/Downloads/Prardhana/app/src/main/java/in/prardhana/app/Store.java:96).

**F07 — P1, code-confirmed: lifecycle state is owned by the screen instance.**

Raw import/AI threads outlive `MainActivity`; busy flags and result maps live in that Activity. Rotation can detach progress and permit duplicate work from a new screen. Checks against `isDestroyed()` prevent some stale UI updates but do not make the work resumable. Use lifecycle-independent operation state, durable import checkpoints and observable screen state. Keep the local ledger usable during network failure. [Activity state](C:/Users/nande/Downloads/Prardhana/app/src/main/java/in/prardhana/app/MainActivity.java:14), [import](C:/Users/nande/Downloads/Prardhana/app/src/main/java/in/prardhana/app/MainActivity.java:213).

**F08 — P1, design-only: false accounting semantics.**

The Claude brief puts family payments into “Moved,” alongside own-account transfers. Money sent to family is still external outflow unless an explicitly chosen accounting scope says otherwise. The overview proposal uses ₹2,000 to separate everyday payments from big moves and suggests account merging by suffix. Neither amount size nor matching suffix proves a transfer, purpose or account identity. Use amount only to prioritize review; use explicit ownership/link confirmation for exclusions. Mandate ceilings, estimated repeats and completed debits remain different types. [Family definition](<C:/Users/nande/Downloads/Prardhana/clauds work/CLAUDE_Stitch_Design_Brief.md:38>), [suffix proposal](<C:/Users/nande/Downloads/Prardhana/clauds work/OVERVIEW_DESIGN.md:90>).

**F09 — P1 if connected pilot stays: deletion has a lost-response recovery hole.**

If `/v1/me` succeeds but its response is lost, the client retains its token. Retrying receives 401 because the installation no longer exists; `removeRemote` throws before local cleanup. Full local reset also discards the credential needed to delete previous uploads. Provide a durable deletion state and define an idempotent deletion contract; do not claim success merely because connectivity failed. Test deletion-response loss and reset while offline. [Client deletion](C:/Users/nande/Downloads/Prardhana/app/src/main/java/in/prardhana/app/PilotSync.java:39), [server authorization/deletion](C:/Users/nande/Downloads/Prardhana/server/pilot.cjs:68).

**F10 — P1 if distributing through the service: release identity is asserted, not verified.**

The service trusts a filename `app-release.apk` and a separate JSON file. It does not inspect signing identity, debuggability or embedded version. Its test serves plain text called “signed release,” proving routing rather than signature enforcement. Build metadata uses `finalizedBy`, which is not itself proof of successful verified publication. Produce an immutable release bundle only after APK inspection/signature verification and atomically publish matching APK/hash/version metadata. Hash once per release; currently every release/status lookup synchronously rereads and hashes the APK. [Release route](C:/Users/nande/Downloads/Prardhana/server/pilot.cjs:41), [metadata task](C:/Users/nande/Downloads/Prardhana/app/build.gradle:30), [Gradle finalizer behavior](https://docs.gradle.org/current/userguide/controlling_task_execution.html).

**F11 — P2, code-confirmed: AI has rate limits but no durable spending budget.**

The service limits output to 2,400 tokens, allows two concurrent requests and 30 requests/hour per process. That is not an account-specific cost ceiling: restarts reset the window, replicas multiply it, and repeats of identical findings can be billed again. Client results exist only in Activity memory. Defer AI. Before reintroducing it, use a durable quota, request idempotency, cache by findings/model/prompt version, actual usage accounting and timeout/cancellation behavior. A single process can permit up to 72,000 configured output-token capacity per hour; this is not actual usage or a currency-cost estimate. [AI service](C:/Users/nande/Downloads/Prardhana/server/insights.cjs:22).

### Messy Repo Tech Debt

- **Competing specifications:** Figma exports, overview v2/v3, two Stitch briefs and implementation describe different navigation, privacy promises and inference rules. The Claude brief promises optional encrypted backup; the Codex brief explicitly says authentication must not imply backup. Current Android excludes backup and device transfer. Adopt one versioned MVP behavior specification and mark the others as dated exploration.
- **Duplicated logic:** `InsightEngine` and `RecurringEngine` implement different recurrence products. `MainActivity.matches` duplicates database filtering; `Insights.local` computes a local `spent` value that is not used in its final call. Remove inactive duplicates after verifying callers; retain one authoritative definition per financial calculation.
- **Weak data contracts:** `JSONObject.opt*` makes missing fields silently become zero/empty. SQL columns mirror JSON data. Use typed money/direction/status/identity models and one serialization boundary; do not spread schema interpretation through UI code.
- **Compressed source:** long, multi-action lines obscure ownership, transaction boundaries and exception behavior. Format touched files and extract responsibilities before adding more features. Java is not the problem; changing languages would not fix these contracts.
- **Two admin data modes share state:** the connected admin replaces the same `records` used by local-file imports; the next refresh overwrites that view. Separate the stores or retire legacy imports. [Connected records](C:/Users/nande/Downloads/Prardhana/admin/pilot.js:8), [local imports](C:/Users/nande/Downloads/Prardhana/admin/app.js:4).
- **Reproducibility gaps:** pure-Java probes and Node tests are outside the standard Gradle test task; no checked-in CI workflow or unified verification command was found. The working tree includes untracked production `LedgerWork.java` and `CorrectnessTest.java`; testing this checkout is not proof a fresh clone has them. The build warns that AGP 8.5.1 was tested only through SDK 34 while this app compiles against 35.
- **Research and specifications share an ignored directory:** `clauds work/` contains raw research, databases, generated outputs and the only copies of important design decisions. Promote reviewed, sanitized specifications and synthetic fixtures into tracked `docs/` and test fixtures. Keep private data separately controlled; `.gitignore` prevents normal tracking but is not an access-control or retention policy. Do not blindly delete research or commit the whole folder.

### Edge Case Blindspots and required verification

| Failure scenario | Required invariant |
|---|---|
| Network disappears during use | Viewing, capture, correction and import remain functional; no generic network gate. |
| Process killed halfway through import | Resume from a checkpoint or idempotently restart; committed batches and overrides survive. |
| Permission revoked during import | Stop promptly, preserve committed work, show interrupted coverage rather than “complete.” |
| Notification repeats; live SMS overlaps inbox import | A known observation is idempotent; distinct real purchases survive. Ambiguous copies remain reviewable. |
| Reset races with capture/import | No observation accepted before reset reappears afterward, including delayed SMS callbacks. |
| Storage full or DB write fails | No success UI or partial evidence/movement commit; recoverable error remains visible. |
| Transaction corrected/deleted | Home, widget, event links and any caches reflect the same committed revision. |
| Midnight, delayed SMS, timezone changes | Distinguish received time from effective transaction time; recompute period summaries consistently. |
| Notification disconnected/OEM background restriction | Show observable source health and gaps. Do not equate permission granted with reliable capture. |
| Duplicate account suffixes, multiple SIMs | Keep uncertain source/account identities distinct; no ownership inference from the suffix. |
| Partial refund, card repayment, BNPL settlement | Preserve distinct movements; do not call gross outflow verified consumption or invent automatic reconciliation. |
| Large text, TalkBack, keyboard, rotation | Core setup/review actions remain reachable and labelled; drafts and review position survive. |

Google Play distribution is a separate early constraint: SMS-based money management is a listed exception category, but permission use requires declaration and review/approval. Sideloading proves neither eligibility nor Play acceptance. Decide the intended channel before committing to the onboarding path. [Google Play SMS policy](https://support.google.com/googleplay/android-developer/answer/10208820?hl=en).

## STEP 3: THE MVP ROADMAP ENGINE

### Phase 1: Core Engine & Essential UI

Execute in this order. Owner labels indicate responsibilities, not a requirement to hire separate people.

| Order | Work package / owner | Acceptance gate |
|---|---|---|
| 1 | Freeze the behavior contract and distribution scope / product + Android | Three destinations; recorded outflow semantics; explicit unsupported cases; all briefs marked implemented/proposed/deferred. No sign-in, cloud backup or inferred financial certainty promised. |
| 2 | Repair amount parsing and correction / domain + Android | Both reproduced parser failures rejected/fixed; every saved amount editable; integer-paise validation; originals and overrides distinct; re-import preserves corrections. |
| 3 | Establish one write path and transaction boundaries / data | Observation identity, movement, tombstone and dependent invalidation commit together. Reset generation applies to every producer. No success result before commit. |
| 4 | Build source setup, coverage, Home and prioritized review / Android | Fresh install shows setup rather than reassuring zero; denied access has a usable local fallback; import leads directly to useful activity; user can correct a high-impact entry and see its total change offline. |
| 5 | Remove blocking reads and unstable screen ownership / Android | Database and parsing work off the main thread; bounded recycled list; state survives rotation; capture/import do not require the original Activity instance. |
| 6 | Establish privacy/release boundary / Android + release | No raw message persistence added; optional external sharing absent from the consumer loop; APK identity/signing checked for pilot distribution; sensitive research excluded from build/test inputs. |

**Phase 1 exit:** demonstrate fresh install → permission accepted or declined → local result → amount correction → correct total → reopen → same result, with network disabled. Any deterministic wrong-amount case or silent correction loss blocks exit. Keep existing pilot users' data and rollback path when removing UI features.

Recommended internal boundary, within the existing Android app:

```text
SMS / notifications / manual input
            ↓
source policy + pure parser + observation identity
            ↓
transactional ledger repository ← explicit user overrides
            ↓
typed queries / revisioned summaries
            ↓
lifecycle-owned screen state → Home / Activity / Settings

optional diagnostic export reads a separate, consented projection
```

Retain Java and SQLite initially. Extract domain, capture, storage and presentation packages incrementally. A Compose or Room migration is optional follow-up work, not a prerequisite for correctness. Generated HTML/Tailwind is a design reference, not drop-in native Android UI.

### Phase 2: Refinement & Error Handling

| Order | Work package / owner | Acceptance gate |
|---|---|---|
| 7 | Durable capture/import recovery / Android + data | Process-death, queue-pressure, revoked permission and reset-race cases pass; missing coverage visible; resumable import does not duplicate observations. |
| 8 | Derived-state stability and safe caching / domain + data | Every mutation updates a ledger revision; summary caches key on revision, period and timezone; event statuses revalidate; midnight and widget behavior tested. Add caching only where measured. |
| 9 | Undo and recoverability / Android + data | Delete/review/group changes reversible; migration failure preserves prior data. Before wider use as a primary record, provide validated protected local export/restore or explicitly constrain the pilot to disposable data. |
| 10 | Narrow pilot feedback and deletion repair, if retained / service + Android | Offline does not block local use; repeated reports idempotent; deletion response loss handled; stopping sharing stops subsequent work; clocks cannot permanently freeze newer snapshots behind a future timestamp. |
| 11 | Reproducible quality and device gates / release + QA | One command runs Android, standalone Java and Node suites from a clean checkout; release artifact checked; real-device lifecycle/permission testing recorded. |

Proposed performance gates, to measure rather than claim: on a named target mid-range Android phone with 20,000 synthetic movements, cached Home usable within 1 second, review save reflected within 300 ms at p95, and no ANR during import plus scrolling. Record device, OS, cold/warm conditions and distribution of timings. Validate at least an API 26-compatible environment, a current target environment and representative restricted-background OEM devices before broad rollout. Host timing is not a handset benchmark.

Product validation should measure whether a tester can explain the total, correct a mistake and return without assistance. Parser acceptance requires a labelled fixture corpus with amount/direction precision and recall reported separately by supported template/source; review-tap percentage cannot substitute for ground truth. Missing messages make complete real-world spending recall unknowable without an independent reference.

### Phase 3: Post-MVP Backlog

Cut these from the active MVP queue now. Reintroduce only against the listed dependency.

| Deferred scope | Required dependency |
|---|---|
| AI explanations, chat, habit prose, year-in-money stories | Demonstrated benefit beyond deterministic wording; durable cost budget and opt-in data contract. |
| Deep charts, six-month comparisons, heatmaps | Comparable coverage and period semantics, usable unknown states, validated aggregates. |
| Recurring discovery, calendars, committed totals, forecasts | Stable series identity, one recurrence engine, separation of stated amounts/ceilings/estimates, user resolution. |
| Automatic transfer detection and account-mask merging | Explicit ownership, ambiguous-match handling, reversible associations and validated fixtures. |
| Google/mobile sign-in, profile, encrypted cloud backup, second phone | Actual recovery/sync threat model, key ownership, conflict policy and deletion lifecycle. |
| Large vendor directory, receipt enrichment, inferred habit naming | Evidence that the source identifies the entity; collision and false-link evaluation. |
| Multiple widgets, custom money palettes, elaborate animations | Stable core state, accessibility and demonstrated usage. |
| Full consumer-facing pattern lab and fleet analytics | A specific operational decision that cannot be made with simpler internal tools. |

Accessibility, clear error handling and honest privacy language are essential in Phases 1–2. Defer expanding languages only if the pilot explicitly supports a narrower set; do not promise multilingual parsing because the screen has a language picker.
